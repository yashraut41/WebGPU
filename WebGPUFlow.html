WebGPU learning map

The Graphics Factory Analogy

A systematic mental model for the Blue Screen → Triangle → Perspective Triangle → Colored Triangle programs. The goal is not to memorize APIs. The goal is to understand who owns what, why it exists, and how data moves.

🏭 Device = Factory 📐 Layout = Blueprint 📦 Buffer = Storage 🧾 BindGroup = Filled resource package ⚙️ Pipeline = Production recipe 📝 CommandEncoder = Order writer 🚚 Queue = Delivery lane 🎨 Shader = GPU worker

1. The whole picture first

Think of WebGPU as a graphics factory. JavaScript does not directly draw pixels. It prepares resources, creates a production recipe, records an order, and submits that order to the GPU.

2. Adapter vs Device

Real-world
Factory / hardware selection

An adapter represents an available graphics capability you can choose from.

→
WebGPU
GPUAdapter → GPUDevice

The device is the working interface through which your program creates GPU resources and work.

const gpu = navigator.gpu; const adapter = await gpu.requestAdapter(); device = await adapter.requestDevice();
Mental shortcut: Adapter = “what can I use?” Device = “give me the interface I will actually use.”

3. Queue

Real-world
Delivery lane

Your finished production order goes onto the delivery lane.

→
WebGPU
GPUQueue

The queue receives finished command buffers for GPU execution.

const commandBuffer = commandEncoder.finish(); queue.submit([commandBuffer]);
Important: Queue is not where you build the commands. You build them with a CommandEncoder and submit the finished CommandBuffer.

4. Resources: storage and instructions

📦 GPUBuffer = factory storage

A GPUBuffer is GPU-side storage. In your programs it holds vertex data or uniform data.

buffer_position = device.createBuffer(...); queue.writeBuffer(buffer_position, ...); buffer_mvpUniform = device.createBuffer(...);

🎨 GPUShaderModule = worker instructions

A shader module contains WGSL instructions that describe what GPU shader workers do.

const shaderModule_vertexShader = device.createShaderModule({ code: vertexShaderSourceCode });

5. BindGroupLayout vs BindGroup — the key analogy

Blueprint
BindGroupLayout

Defines what must exist in each binding slot: type, binding number, and shader visibility.

binding: 0, visibility: GPUShaderStage.VERTEX, buffer: { type: "uniform" }
→
Actual package
BindGroup

Fills that blueprint with an actual resource, such as your MVP uniform buffer.

binding: 0, resource: { buffer: buffer_mvpUniform }
Think hotel: BindGroupLayout says “Room 0 must contain a uniform-buffer resource.” BindGroup says “Here is the actual room with this actual uniform buffer.”

6. Why the shader says @group(0) @binding(0)

The WGSL shader and JavaScript must agree about the resource address.

WGSL@group(0) @binding(0)
↔
PipelineLayoutGroup 0 layout
↔
BindGroupLayoutBinding 0 = uniform
↔
BindGroupActual MVP buffer
↔
MVP UniformActual matrix data
@group(0) @binding(0) var<uniform> mvpUniform : MVPUniform;

This is a resource-binding contract. It is different from vertex-buffer locations.

7. Pipeline = production recipe

The RenderPipeline packages the rules needed to process your draw call.

+
Vertex StateVertex shader + input layout
+
Fragment StateFragment shader + target
+
Primitive Statetriangle-list, culling...
→
RenderPipelineComplete recipe
Do not confuse: RenderPass is the production session. RenderPipeline is the recipe/configuration used during that session.

8. Vertex data: the colored triangle

In the colored-triangle program, each vertex carries two attributes: position and color.

Position buffer — slot 0

setVertexBuffer(0, buffer_position) @location(0) vPos : vec4<f32>

Slot 0 is described as position data.

Color buffer — slot 1

setVertexBuffer(1, buffer_color) @location(1) col : vec4<f32>

Slot 1 is described as color data.

Critical distinction: setVertexBuffer() connects vertex attributes. setBindGroup() connects shader resources such as uniforms.

9. The vertex-input contract

JavaScript pipeline description WGSL Meaning
shaderLocation: 0
format: "float32x4"		 @location(0) vPos : vec4<f32> Position attribute enters the vertex shader.
shaderLocation: 1
format: "float32x4"		 @location(1) col : vec4<f32> Color attribute enters the vertex shader.
Analogy: The pipeline is the loading dock specification. “Truck slot 0 must contain four 32-bit floats for position; truck slot 1 must contain four 32-bit floats for color.”

10. VertexOutput = the handoff package

This is the part that connects the vertex shader to the fragment shader.

Vertex worker
Produces a package
struct VertexOutput { @builtin(position) position : vec4<f32>, @location(0) color : vec4<f32> };
→
Fragment worker
Receives the package
@fragment fn main(output: VertexOutput) -> @location(0) vec4<f32> { return output.color; }
Very important: the variable name output is arbitrary. What matters is the interface locations and built-ins. The vertex shader returns a VertexOutput; the fragment shader receives the corresponding interpolated values.

11. The two different kinds of “location”

Input location

Vertex buffer ↓ @location(0) vPos @location(1) col

These describe data entering the vertex shader from vertex buffers.

Inter-stage location

Vertex shader ↓ VertexOutput.color ↓ @location(0) ↓ Fragment shader

This describes data traveling from vertex shader to fragment shader.

Same syntax, different interface: @location(0) in the vertex input and @location(0) in VertexOutput are not the same binding mechanism.

14. The actual display() command sequence

1
Create command encoder
const commandEncoder = device.createCommandEncoder();
2
Get current canvas texture
context.getCurrentTexture().createView()
3
Calculate and upload MVP
queue.writeBuffer(buffer_mvpUniform, ...);
4
Begin render pass
commandEncoder.beginRenderPass(renderPassDescriptor)
5
Select recipe
renderPassEncoder.setPipeline(render_pipeline);
6
Attach vertex data
setVertexBuffer(0, buffer_position); setVertexBuffer(1, buffer_color);
7
Attach resource package
renderPassEncoder.setBindGroup(0, bindingGroup_mvpUniform);
8
Draw
renderPassEncoder.draw(3);
9
Finish and submit
const commandBuffer = commandEncoder.finish(); queue.submit([commandBuffer]);
